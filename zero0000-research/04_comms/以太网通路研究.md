# 以太网通路研究（RTL8211FI + Kintex-7）

> 归属：L4 通信通路  
> 证据等级：✅ 确认（数据手册/照片可直接支撑） / 🔶 推断（器件典型用法） / ❓ 待证（需固件分析或实物实验）  
> 前置输入：L1 确认板载 RTL8211FI + RJ45 ✅；L3 确认 RTL8211F 系列仅支持 RGMII，故 FPGA↔PHY 为 RGMII ✅

---

## 1. 硬件通路要点

| 项 | 内容 | 等级 |
|----|------|------|
| PHY | RTL8211FI：10/100/1000BASE-T 千兆 PHY，`-I` 为工业温度版 | ✅ |
| FPGA 接口 | RGMII（4bit DDR 数据 + 125 MHz 时钟，1000M 模式） | ✅（系列仅支持 RGMII） |
| 管理接口 | MDC/MDIO（Clause 22），PHY 地址由上电 strap 引脚决定 | ✅（接口）/ ❓（地址值） |
| RGMII 时序 | RTL8211F 支持片内 TX/RX delay（寄存器或 strap 使能），决定 FPGA 侧是否需 IDELAY/ODELAY 补偿 | ❓（本板配置） |
| MAC | **Kintex-7 无硬核 MAC**（区别于 Zynq PS-GEM），MAC 必须在 PL 内实现 | ✅ |
| MAC 实现候选 | ① Xilinx TEMAC IP（需 license）② 开源 verilog-ethernet / LiteEth ③ MicroBlaze + AXI EthernetLite/TEMAC + lwIP | 🔶（本板用哪种 ❓，由 E1 mcs 特征提取判定） |
| 线速上限 | GbE ≈ 118 MB/s（UDP 有效载荷，标准帧约 114 MB/s） | ✅ |

**关键判断 🔶**：本板同时有 FT600Q（≈340~400 MB/s）与 GbE（≈118 MB/s）。GbE 带宽不足以承载 ADC 满速流，故其角色更可能是**控制面 + 低速/抽取后数据面**，或作为 USB 之外的备份数据口。此判断与 L3 带宽预算一致，可由 E4（端口行为）证伪。

## 2. DAQ/SDR 板卡的典型以太网用法

### 2.1 控制面 vs 数据面

| 维度 | 控制面 | 数据面 |
|------|--------|--------|
| 内容 | 寄存器读写、采集启停、触发/深度参数、状态查询 | ADC 样本流、DAC 波形下发 |
| 包特征 | 小包（几十字节）、低频率、请求-应答 | 大包（接近 MTU 或 jumbo）、高速率、单向为主 |
| 协议惯例 | UDP 固定端口的自定义命令帧（少数用 TCP） | 原始 UDP 流 + 自定义包头（序号/时间戳/通道号） |
| 可靠性 | 应答 + 上位机重试 | 通常**不重传**，靠序号检测丢包（DAQ 惯例） |
| 典型参照 | UHD/CHDR（USRP）、白兔/嵌入式仪器的 UDP 寄存器协议 | USRP UDP 流、各类采集卡厂商私有 UDP 流 |

**为什么几乎都用 UDP 🔶**：FPGA 纯逻辑实现 TCP 状态机成本高；UDP 收发在硬件里只需固定包头拼装，且 DAQ 场景允许丢包（由序号补救）。若 mcs 中发现 lwIP/MicroBlaze 特征，则 TCP 控制面也可能存在 ❓。

### 2.2 常见协议形态（判别用清单）

| 形态 | 特征 | 对应实现线索 |
|------|------|---------------|
| 纯自定义 UDP | 固定 IP/MAC 写死在固件；可能不答 ARP/ICMP，需上位机静态 ARP | mcs 字符串中出现点分 IP、MAC 常量 |
| lwIP 软协议栈 | 答 ARP/ICMP，可能有 DHCP；控制面可为 TCP | mcs 出现 `lwip`、`microblaze` 特征 |
| iperf 风格测试流 | 固件内置打流/收流逻辑用于吞吐验证 | 端口 5001/5201 或连续满速 UDP |
| 原始以太网帧（无 IP） | 自定义 EtherType，局域网直连 | 抓包见非 0x0800/0x0806 EtherType |

## 3. 无实物阶段 Checklist

1. **E1 联动**：在 mcs 提取物中搜索 IP 地址（点分十进制正则）、MAC 常量、`lwip`/`eth`/`udp` 字符串、TEMAC/AXI Ethernet IP 核特征 → 判定 MAC 实现与协议形态 ❓→🔶。
2. **照片核对**：放大 RTL8211FI 周边，确认 RGMII 走线到 FPGA 哪个 bank、strap 电阻（PHY 地址、TX/RX delay、LED 配置）❓→🔶。
3. **上位机脚本预备**：Python `socket` UDP 收发脚本（可配 IP/端口/静态 ARP）、丢包统计（按序号）、简单命令帧构造器。
4. **主机环境预备**：千兆网卡直连方案；静态 IP 网段预案（常见默认 192.168.0.x / 192.168.1.x ❓）；`sysctl` 增大 UDP 接收缓冲；确认网卡支持 jumbo（备用）。
5. **抓包工具预备**：Wireshark/tcpdump 安装；准备按 MAC/EtherType 过滤表达式（应对无 IP 的原始帧场景）。
6. **测试计划成文**：把第 4 节实物步骤按"可直接照做"粒度写入 `05_tests/` 模板。

## 4. 有实物阶段步骤（抓包主线）

1. **物理层**：直连主机网卡，观察 RJ45 LED 与 `ethtool` 协商结果（1000M/全双工为期望值）。
2. **被动监听**：主机网卡不配 IP，先 `tcpdump -i <if> -w boot.pcap` 抓上电流量——固件若主动发 ARP/DHCP/组播即可直接得到板卡 IP/MAC ❓→✅。
3. **主动探测**：按第 3 步线索（或常见网段猜测）配主机 IP，`arping`/`ping` 测试；不通则加静态 ARP 再试 UDP。
4. **端口行为（E4）**：`nmap -sU` 粗扫 + 对候选端口发探测包，区分命令口（有应答）与数据口（单向流）。
5. **协议还原**：Wireshark 抓命令交互与数据流，还原帧结构（包头字段、序号位置、字节序），回填第 2 节判别表。
6. **吞吐与丢包**：命令启动连续采集，用收流脚本统计速率与序号断裂；对照 118 MB/s 线速与 L3 带宽预算。
7. **长稳**：≥30 min 连续收流，记录丢包率、链路重协商次数，写入 `05_tests/`。
